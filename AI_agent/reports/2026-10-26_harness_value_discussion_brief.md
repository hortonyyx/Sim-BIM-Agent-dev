# Sim BIM Agent 当前问题与跨模型讨论背景

日期：2026-10-26。用途：供未参与前期开发的模型和协作者理解现状，独立讨论技术路线、实验设计与下一步优先级。

> 2026-10-26 讨论后补充：用户随后澄清了价值口径，第 1.1 节的“至少快一半”“同模型更省 token”不再是硬性口径，更省主要指提高弱模型承担的比重；同时确认按内容和形式指代 domain。以往通用组实际拿到了 BIM rules（文字）和部分 methods（文字）。结论见[价值口径与对照基线](2026-10-26_harness_value_axes_discussion.md)，本文其余事实不变。

本文保留用户的目标与判断，汇总已核对的实验事实，并把解释和待验证假设单独列出。阅读正文即可参与讨论；末尾的本地证据索引用于进一步复核。没有仓库访问权限时，不需要假装已经检查代码或原始产物。

**目前最重要的结论是：我们尚未证明这套系统在完整交付上实现了更快、更好、更省，但现有实验也不足以证明“给强模型增加可选领域工具就会成为负担”。最近的对照要求工具组走指定的原生构建、审阅和交付路径，它没有完整保留通用组的自由出口。这个实验设计差异必须与实际工程缺陷一起讨论。**

当前程序为 runtime 43、domain 153；最近四次局部建模实验使用的是冻结的 domain 152。domain 153 只修复发布权限故障，尚无新的工作模型复测。本文不启动新实验，不改变质量标准，也不把建议写成已实施结果。

## 1 项目要解决什么问题

用户的毕业设计包含两部分：开发一套从多模态建筑资料生成 Sim BIM 的 Agent，并用它完成一片实际街区的仿真。输入可能包含 textured mesh、建筑平面或立面图、照片与文字描述，资料充分程度不固定。

目标产物是具有建筑空间、边界、开口、连接关系和依据的轻量源 BIM。它需要支撑后续仿真派生、可视化和人工查看，不能只生成外观相似的三维模型。源 BIM 与特定仿真后端的热区、拆面、物性及系统配置是不同层次，不能因为源文件生成成功就宣称已完成仿真。

用户的核心担忧是：如果相同模型在通用 Agent 中临时编写脚本，就能以相近甚至更低的成本交付同等产物，那么我们开发的 Agent 到底增加了什么？“有很多工具”“能输出规定格式”“有自研运行循环”都不足以单独回答这一点。

同时，用户也明确指出，项目提供的是系统性的能力，包括规定好的数据接口、几何工具、可视化和平台。不能因为某个强模型可以临时实现功能，就把这些积累全部判为无用。另一种可能的价值是：让能力较弱或成本更低的模型完成原本完成不了的任务，或者把强模型积累的方法沉淀为其他模型也能使用的能力。

### 1.1 用户已经给定的目标

| 目标 | 用户要求 | 当前状态 |
|---|---|---|
| 更快 | 同模型、同质量下至少快一半才有意义；幸福中心、利苑单 Agent 完整交付均应在 10 分钟内 | 尚未证明达成 |
| 更好 | 更高的交付质量、更合理的建筑推断，最低质量不能降 | 尚未证明稳定优于通用对照 |
| 更省 | 包括同模型更省 token，以及较便宜模型可达到要求；失败和恢复也计入 | 尚未证明 |
| 后续分工 | 完整交付压到 5 分钟；先把单 Agent 工序优化好 | 尚未进入新的生产分工验收 |
| 通用性 | 面向不同输入方式和信息充分程度，允许用户接入自己的模型 | 不能靠两个案例的专用答案成立 |
| 仿真应用 | 最终完成实际街区的仿真链路 | 不由当前 source BIM 生成实验代替 |

“10 分钟”是完整合格交付时间，不是首稿时间。若模型在 8 分钟时保存了候选，但在 15 分钟才完成必要检查和导出，就不能算 8 分钟交付。质量失败的快速产物也不能作为合格交付成绩。

用户允许不同模型效果有波动，但希望系统尽可能稳定地交出可用结果。这里仍需明确一个产品边界：对无法满足最低质量的模型或输入，应保留可恢复候选并明确缺口，不能用降低标准或把失败标成成功来实现“总能输出”。

## 2 我们所说的 harness 包含什么

项目采用以下划分：Sim BIM Agent 由工作模型与 harness 组成；harness 又分为 runtime 和 domain。

| 层次 | 当前职责 | 与本次争议的关系 |
|---|---|---|
| 工作模型 | 理解资料，判断建筑用途、形体、空间组织和必要推断，选择工具与修复策略 | 强模型可能自行构造几何，也可能选择现成工具；选择质量需要实测 |
| Runtime | 模型接入、请求和工具循环、上下文、预算、事件记录、恢复与委派 | 自研 runtime 与 Codex runtime 的价值应单独比较 |
| BIM 数据合同 | 空间身份、显式边界、开口宿主、接触与连接、坐标、依据、摘要与版本 | 是共同输出与下游集成的基础；定义格式不等于模型不能自行生成格式 |
| 几何内核 | 参数展开、坐标变换、规整、共享边界、接触关系、开口宿主和源 BIM 编译 | 可以免去大量底层编码；目前尚未稳定转化为端到端收益 |
| 领域工具 | 看图、mesh 观察与量测、构建、修改、回叠、检查和交付 | 工具是否易发现、易组合、可替代，以及回复开销，都会影响实际使用 |
| 方法与指导 | 按输入提供方法、短入口、参考、建筑原则和错误反馈 | 原则主要由模型实施；长说明及不明确的能力边界可能增加工作量 |
| 平台与可视化 | 查看统一产物、关联证据、保留运行和候选、提供交付入口 | 有工程用途，但需进一步证明减少人工、提高可靠性或促进仿真闭环 |

现有系统的意图不是让所有任务经过固定编号的阶段。工具和方法中存在可选能力，例如额外构造检查，并不要求每次调用。与此同时，原生候选的合法性、审阅覆盖和原生完成有自己的契约。**“没有固定总流程”不等于“每一种最终交付路径都同样开放”。**

最近的实验把 domain SDK 放在 Codex 上运行，因此两组都使用 Codex 的通用运行能力。这些结果主要用于研究领域工具路径，不能直接归因于自研 runtime。

### 2.1 几种容易混淆的完成状态

| 状态 | 代表什么 | 不代表什么 |
|---|---|---|
| 首个 source 已保存 | 已有可解析的源模型字节 | 已通过建筑验收或已经可交付 |
| 几何和结构检查通过 | 检查范围内的语法、几何、宿主、引用等满足要求 | 房间布置合理、通道实际可用、与图纸一致 |
| 原生 finish 成功 | 原生路径对当前候选完成其既定核验与绑定 | 公共发布必然成功，或独立质量必然通过 |
| 公共交付完成 | 约定文件、查看器和绑定信息交付完成，任务相关进程结束 | 事后独立建筑质量自动通过 |
| 独立建筑质量通过 | 独立评阅在约定范围内认可产物 | 施工图准确、所有规范合规或特定仿真后端已接通 |

## 3 关于细度和质量 已经讨论清楚的原则

这部分与当前效率问题直接相关。此前讨论过两个用户档位，以及增加一个自动选择档位的可能；后来用户更倾向由输入信息决定合理细度。是否最终只保留自动模式，仍未定案。

### 3.1 粗档的目的

用户反复强调：允许较粗，是为了更高效地完成、减少没有依据的细化，而不是追求一个粗糙结果。如果模型已经读懂核心筒各房间的准确位置和关系，就应该保留这些信息，不能为了符合“粗档”再把它们合并。

不应先生成精细模型，再删减成粗模型；也不应把固定返工次数直接当作档位。只返工一次的结果可能很好，也可能根本不合格。过程限制可以帮助控制投入，但结果仍必须达到最低质量。

实施判断主要交给模型，以原则、案例和反例指导。规则无法穷尽所有建筑；后续可以让空间判断能力较强的调度员承担决策，但目前先优化单 Agent。

### 3.2 用户给出的具体例子

**只有 textured mesh 的办公或酒店类建筑：**

- 最低可接受产物应保留主要外轮廓、凹凸、裙楼、顶部及 mesh 已表达的关键形体，不能简化成一个规则盒子。立面、楼层和窗户应基本对位；门可以适度放宽。
- 内部需要合理推断整体组织。例如 L 形建筑可能对应两向走廊与依次排布的房间。必要楼电梯、卫生间、管井、底层入口等功能及水平、竖向交通应合理推断；需要人员或维护进入的空间应有合乎用途的可达路径，用途和上下关系应合理。
- 可以保留较大的功能空间，不必一定拆出每个房间。但“大空间”不能掩盖必要交通和辅助功能缺失，也不能让窗组与内部空间发生明显矛盾。
- 更细的结果可以进一步划分房间；若明确是酒店，也可能推断客房内卫生间。若 mesh 用贴图将真实三维细节压在简单表面上，较细处理还可能根据纹理恢复有依据的几何或功能，而不只是照搬 mesh 表面。
- 无平面图时，继续细分往往缺少证据，自动模式通常应停在合理组织层面。缺失某一立面时，按整体采用的细度作一致推断，不另设一套降低底线的规则。

**幸福中心和利苑这类同时带图纸的案例：**

- 已知平面信息应充分利用。标准层核心筒位置、功能的相对位置和连接关系必须正确；局部尺寸可适度简化。
- 功能分区与实体隔墙应分开表达；图纸明确没有隔墙的地方，不能为了增加细度而虚构实体分隔。
- 一些小的低层形体变化可以不做，卫生间与附属管井等可以在确有表达收益时合并；但已正确读出的细节无需主动抹掉。
- 底层资料缺失时，可以采用较简单的大空间组织；进一步推断沿街商业或入口分区应有依据，不把无依据的复杂化当作更好。
- 更细主要体现为形体变化和平面还原更准确，而不是穷尽房间细节。仿真后端需要的进一步分区、拆面，应由相应派生流程处理。

以上是用户对最低可用性和投入价值的说明，不是一个已经编码完的穷尽规则集。主要目标是忠实表达已知信息、补足必要关系，并停止低收益展开。这些原则应适用于所有输入方式，而不只用于 textured mesh。

## 4 当前争议 为什么可选工具还可能成为负担

用户最新的问题可以概括为：

> 我们并没有强制强模型使用所有工具，也没有强制它走固定流程。强模型可以按需选择；有更省的现成路径就直接用，没有就自行实现。增加的负担是否只是多了一些任务和工具说明？

这个质疑成立，必须先纠正此前过宽的判断。

### 4.1 最近的实验并非完全可选工具实验

最新 B 组的真实提示明确要求：从 SDK 入口开始，走 build、实际视图、review、finish_to；发布所选原生候选；禁止手工重构或修改该源、自行复制文件或编写发布哈希。共同收件器也会对 B 验证原生 finish 与发布绑定。

其中两段原文是：

> Start with .../src/agent/SDK.md and follow its build, actual views, review and finish_to path.

> Do not manually reconstruct or modify the selected source, copy files, or write publication hashes yourself.

A 组可以直接编写 materialized source，再由共同收件器使用相同渲染器生成展示。B 有普通 Python、shell 和看图能力，但最终不能像 A 一样自由退出到手写源模型路径。

因此，两组的最终 BIM 数据结构和独立建筑底线相同，**生产路径与来源证明义务并不相同**。这轮能诊断规定的原生路径，却不能隔离“多提供一套可选工具”的因果影响。

这并不意味着原生来源记录没有价值，也不意味着允许伪造 review 或 receipt。问题在于：如果来源证明和审阅证据属于必要交付，应对两组设置等价义务；如果研究的是工具增量价值，就应让工具组保留通用出口，采用原生路径时再记录真实的原生证据。

### 4.2 也不能反过来说 B 的每一步都被强制

完整参考、工具目录、额外 check_plan 和自写检查器并非全部强制。最新两个 B 样本没有调用 check_plan，核心筒样本仍自主阅读了长参考并补写自检。这部分需要继续研究模型为什么这样选择，不能全部归给实验约束。

原入场清单也未开启严格的 drawing_review_policy；不能后来把所有辅助图都必须单独登记审阅，当作这次原本就有的硬门槛。平面覆盖与实际审阅仍有原生要求，辅助剖面仍是建筑判断和独立质量的依据。

### 4.3 真正完全可选时 仍有哪些待测成本

多一些说明会增加输入，但成本可能通过模型行为继续放大：发现工具、理解适用范围、选接口、适配中间表示、处理工具反馈，以及在不适合时迁回通用路径，都可能增加模型回合。即使一个选择看起来合理，模型也未必预知工具内部成本或尚未暴露的能力缺口。

这些是机制假设，不是已经分离测出的成本。若工具入口短、契约清楚、反馈可信、替代路径保留，它也完全可能省掉更多工作。不能从“存在这些成本”直接跳到“应该撤掉工具”，也不能从“模型理论上能不调用”直接跳到“提供工具绝无成本”。

真正需要测的是：**在通用能力和同一交付义务保持不变时，可选领域能力是否让模型更快、更稳、更省，或者让较低能力模型达到此前达不到的质量。**

## 5 历史整案结果 为什么开始怀疑系统价值

### 5.1 最初的模型结果和用户判断

用户接受过 6.1 Sol 的幸福中心结果，主要问题是耗时；6 Sol 的利苑结果不被接受。6 Sol 有正式产物，不是完全没有生成结果。其失败可能涉及模型识读、表达选择、图像投递或指导等因素，尚未完成独立归因。

已确认的一处问题是：利苑原图中斜向核心筒被上游声明为轴对齐矩形，最终源模型沿用了该声明。对这一处，不能说是内核把正确旋转几何改错；但也不能仅据此认定模型能力永久不足，图片实际进入模型的载荷等条件仍需核查。

### 5.2 早期幸福中心与通用 Codex 对照

同为 6.1 Sol/high、同一组原始资料、相同最终 BIM 出口。通用组不获得本项目的领域工具、编译器、历史答案或标杆，但可以使用通用工具和自行编程。

这里的 one-shot 指一次初始自主任务、没有人工续问；它仍会多轮调用工具、检查和修复，不是一次无工具模型回答。

| 指标 | 自动细度的原 harness | 通用 Codex |
|---|---:|---:|
| 进程端到端 | 27:14.99 | 24:38.11 |
| harness 内部 runtime | 26:35.98 | 不适用 |
| 首有效保存或首源文件 | runtime 内首有效保存 13:29.86 | 进程内首文件 14:34.35，当时未作外部有效性验证 |
| reported total tokens | 2,828,309 | 2,658,508 |
| 请求或响应记录 | 22 次请求 | 32 个独立 usage 响应记录 |

首有效保存和首文件创建不是同一里程碑，不据这两项直接做首稿速度排名。Codex 的环境与合同准备时间另外记录，已知准备下限约 24.1 分钟；这不应消失，也不应与每次运行成本混写。首次配置成本和稳定使用时每次任务成本应分别比较。

Codex 首文件之后仍花了约 10 分 04 秒进行自编检查、几何与拓扑修复、审阅图生成和查看、证据整理与交付，24:38 不是首稿时间。自有 harness 首个有效候选之后为约 13 分 06 秒。后来展示的 Codex 早期首稿由保留脚本逆向撤回后续补丁重建，并核对了历史摘要；这证明恢复内容的身份，不证明它在原时点已经通过验收。

用户查看首稿后认为平面已经很好，后面十多分钟投入带来的提升不值得。他也修正了最初判断：并不能认为 harness 的平面精度更好，Codex 主要在底部和顶部做了不同推断或简化。这个人工判断应保留，不能被“文件合法”或选取个别指标替换。

早期对照支持的事实是：强模型通过通用工具可以生成兼容产物；两种路径各有取舍；现成工具没有在这一轮形成明显交付优势。它不支持任何一方普遍优胜。

### 5.3 后续整案筛选已经出现更快的通用基线

2026-10-25 做过新的两案 A/B 开发筛选。A 为通用 Codex，B 为同一 Codex 加领域 SDK。每组每案一次，期间 B 使用的冻结 domain 版本不同，依赖条件也还未完全对齐，因此不是正式匹配重复。

| 案例与路径 | 首源落盘 | 交付或终态 | 独立建筑质量 |
|---|---:|---|---|
| 幸福中心 A | 5:49.77 | 9:55.61 共同收件器失败 | 不通过：屋顶高低体量反置，消防梯门接入错误 |
| 幸福中心 B，domain 147 | 6:52.20 | 10:58.39 完成交付流程 | 不通过：顶部约 3 m 围护带遗漏 |
| 利苑 A | 6:13.95 | 10:47.53 完成交付流程 | 不通过：电梯入口落入不可通行夹缝 |
| 利苑 B，domain 149 | 10:22.55 | 20:09.84 完成交付流程 | 不通过：西楼梯门过窄，核心通路不可用 |

其中利苑 B 有 24 处楼梯层门约 0.17 m 宽，核心走廊瓶颈约 10–14 mm；几何宿主和连接图可以合法，却不能实际通行。这说明已有确定性检查没有替代建筑合理性判断。

幸福中心 A 的收件器故障后来进行了只读修复重放，但原次失败记录保留。不能事后把它改成 10 分钟内成功。两条 A 的首文件时间也没有对应完整保留下来的最初字节快照，不能拿最终稿冒充首稿。

**后续不能继续只拿早期 24:38 的通用结果作为“快一半”的基线。** 新通用路径已接近 10 分钟，但四份新结果都未过建筑底线。当前真正的问题是获得可重复的合格交付，而不是挑选最慢的旧对照或最快的不合格样本。

## 6 为什么转向两个局部问题

整案同时混有识读、构造、数据表达、几何修复、审阅、发布和模型服务波动。继续反复跑整栋，很难知道某个改动解决了什么。因此后续先用两个新合成局部题检验工具路径。

| 局部题 | 主要内容 | 不覆盖的内容 |
|---|---|---|
| 核心筒题 core | 旋转 31° 的单层平面，8 个具名空间、8 个门，台阶形走廊和两个办公入口 | 不覆盖整栋立面、跨层交通或复杂多模态融合 |
| 屋顶题 roof | 旋转 −17° 的开放维护屋面，实体屏风墙、楼梯间和机房的真实顶盖，3 个空间、2 个门 | 不覆盖完整建筑或实际仿真后端 |

作为建筑题目材料，两组只获得原始图纸、说明与共同出口合同，数值真值与评价材料不供其读取；B 另获得冻结 SDK 及第 4 节所述的原生路径约束。最近一轮使用同一锁定 Python 环境、同一 6.1 Sol/high、同一 Codex runtime、相同图纸、同一渲染器和质量事实。无生产子代理、无人工追加修复提示。

每次局部任务的工程目标是 180 秒；诊断保护为 360 秒、20 个完成响应或 300,000 个已报告 total tokens。token 保护按观察到的回执执行，单次响应可能越线；停止时在途用量仍可能未知。180 秒是这两道局部题的筛选目标，不替代整栋 10 分钟目标。

先前 domain 151 的局部轮中，A 完整交付为 160.83 / 191.78 秒，B 首源为 113.02 / 100.34 秒，但 B 都未完成交付。几何质量当时在局部范围内通过；适配错误、长上下文与收尾消耗了首稿优势。于是下一轮集中修改入口、工具回复和首稿后的交付路径。

## 7 最近一轮局部对照的结果

测试版本为 runtime 43、domain 152。执行顺序 core B → core A → roof A → roof B，每腿仅一次；运行中未修改提示词、冻结包或旧产物。

### 7.1 时间与交付状态

| 题目与路径 | 首个可解析源观察时间 | 原生 finish | 完整公共交付或保护停止 | 完成响应数 |
|---|---:|---:|---|---:|
| core A 通用 | 113.703 s | 不适用 | 140.125 s 完整交付 | 6 |
| core B 原生 SDK | 176.375 s | 223.038 s 成功 | 241.813 s 停止，发布失败 | 11 |
| roof A 通用 | 152.218 s | 不适用 | 169.406 s 完整交付 | 7 |
| roof B 原生 SDK | 110.766 s | 未执行 | 177.281 s 停止，未交付 | 10 |

首源是观察器首次保存完整可解析字节的时间，不保证等于精确写入瞬间。完整交付包括入场、工作模型及子进程结束和共同收件器。保护停止时间不能当成交付耗时。

roof B 首源比 A 快约 27.2%，core B 首源反而慢约 55.1%。两条 B 都没有公共交付成功。即使仅看 core B 的原生 finish，223 秒仍慢于 A 的完整交付 140 秒，因此发布 bug 修复本身不足以实现“至少快一半”。

|---|---:|---:|---:|
| core A | 149,240 | 28,169 | 6,639 |

共 34 个完整 usage 响应，total tokens 已报告下界为 980,462。A 账本完整，B 在途用量未知。货币费用未知，开发和独立评阅会话也没有包含在这份生产账里。

B 两题 total 合计至少比 A 多约 91%。B 已报告输出部分比 A 少约 37%，但 B 的输出本身也是下界，不能据此断言完整输出成本降低了 37%。更短代码和较少的已报输出没有带来已经验证的整次节约。

total 包含缓存输入，不能乘一个单价直接换算货币。后续应同时报告缓存、未缓存输入、输出、失败恢复，以及每次合格交付的成本。

### 7.3 建筑质量与信息完整性

独立评阅查看匿名原图、未改 source 和独立平面/顶面视图。四份源在约定的局部几何、空间组织与通达范围内均通过：核心筒 8 个门宿主正确，台阶走廊和双办公入口保留；屋顶真实维护 deck、完整实体屏风和两间房的封闭顶盖保留。

所有运行只观察到一个保存源版本，保存后未修改几何。因此本轮首稿之后的时间没有变成额外几何细化；但实际看图、检查和发布仍可能有必要，不能把它们一概称为浪费。

两条 B 的 north_axis 都是 null，而题目明确 +Y 为北。实际几何朝向正确，机器可读北向不完整，故不能把“局部几何通过”扩写为“完整质量通过”。A 分别采用 vector 和 direction 键表达 +Y；语义符合题面，但下游对这两种键的兼容性未验证。

匿名包仍含原始 producer 元数据，首次整体读取造成轻微盲审暴露，已在评阅记录中说明。合成题的数值高度吻合也不能用来声称真实栅格识读具备极高测绘精度。这轮没有验证整栋、实际仿真或不同模型之间的能力。

## 8 最近四次运行实际做了什么

### 8.1 core B 原生完成后 发布程序失败

核心过程是：读取短 SDK → 读题与原图 → 额外读取约 21,518 字符的完整参数参考 → 构造并保存、生成显式标定回叠 → 实际查看平面和回叠 → 再读 schema 并写自检与 finish 脚本 → 原生 finish 成功 → 发布目录写入失败 → 排错时触保护。

| 时间窗口 | 可观察动作 |
|---|---|
| 37–39 s | 读 SDK、目录及工具信息 |
| 63–72 s | 读说明、合同和入场信息，返回并实际打开原图 |
| 95–97 s | 主动读取完整参数参考 |
| 126–127 s | 查角色代码，进行门位置坐标换算 |
| 162–178 s | 写并执行构造脚本，保存并回叠；176.375 s 观察到首源 |
| 184 s | 实际打开当前源平面与回叠 |
| 192–193 s | 读候选目录与 schema |
| 217–224 s | 写自检并 finish；原生成功，随后公共发布失败 |

原生 build 耗时约 13.127 秒，其中内部入场约 9.219 秒，compile 约 0.055 秒、export 约 0.189 秒。内核计算本身解释不了 176 秒首源等待。首源到原生 finish 的约 46.663 秒包含看图、读取、生成自检脚本、执行和服务间隙，没有几何修改。

发布失败由 Windows 受限进程对临时 staging 目录的权限导致，写 inputs.json 时报 PermissionError，清理又失败。这是程序缺陷，不是模型建筑能力不足。domain 153 已修复，并用实际受限环境的新单房夹具完成零模型贯通；原失败没有被回写为成功，也没有追加模型补考。

### 8.2 roof B 首源较快 随后遇到真实表达缺口

该样本未在首源前阅读完整参数参考，使用短 SDK 和补充说明构造了屋顶，110.766 秒观察到首源。随后实际看图并自检，发现 north_axis=null，再查长参考、修改接口和源码，尚未调用 finish 就触发 token 保护。

这不是单纯“模型过度纠结一个无关字段”。输入已明确北向，共同合同也要求已知北向不能写成未知；当前正常参数化、source_polygon 和 patch 路径缺少该声明的入口。库中别处有历史方向类型，不等于当前模型正在用的路径可调用。

同时，null 并不是当前原生 finish 的机械阻断。正确表述是：模型发现了语义完整性问题，而现有路径无法直接补足。不能通过让它忽略已知事实来获得更快成绩。

### 8.3 通用路径也有工作量和错误

core A 自写 176 行脚本，构造、校验并交付；core B 构造与 finish 脚本共约 51 行。B 少写了底层代码，但多了读取与往返，未获得总体收益。

roof A 出现过 PowerShell 将 schema 中的 $defs 展开为错误字符串，以及自写凹多边形法向检查器误报。它修的是引用方式和检查器，随后保存成功，没有证据表明它进行了建筑方案返工。不能把通用 Agent 描述成一次就全对。

### 8.4 时间归因能精确到什么程度

能确定的是工具执行时间、读了哪些文档、返回文本量、公开调用、报错、候选变化与完成里程碑。不能把响应之间的全部时间精确拆成“建筑推断多少秒”“阅读说明多少秒”“隐藏思考多少秒”。这些窗口混有输入处理、推理、输出生成、网络和服务等待。

因此，“说明增加了多少字符”“某轮多了几次调用”是证据；“去掉这份说明必然节省两分钟”仍然是假设。单次、固定顺序的实验也无法分离全部服务波动。

## 9 已经做过哪些改动

以下用于避免其他讨论者重复建议已经实现的功能。它们的存在、离线正确性与端到端收益是不同层次。

| 已做改动 | 意图与当前边界 |
|---|---|
| 薄 Python SDK | 普通 Python 可以组合领域工具，循环和变量减少重复声明；SDK 不调用模型、不自动重试或审阅 |
| 共享节点与几何构造辅助 | 减少独立取整、近似门端点造成的错误；保留真实宿主和覆盖检查，不靠扩大容差消除矛盾 |
| primitive_frames、矩形并集、local_baseline | 用局部坐标和共享表达构造旋转平面；最近 B 确实使用，但它们并非全部是本轮新增 |
| 开放围护意图 | 表达开放头顶、实体屏墙和真实房间顶盖，减少“省略形体或虚构房间”的两难；已接入参数路径 |
| 可选 check_plan | 使用同一编译逻辑做无候选检查；check 后 build 会重复编译，并非必选步骤；最近 B 没有使用 |
| 短 SDK 入口 | 常用格式与正常使用示例直接可见，长参考按需；模型仍可能主动阅读长参考 |
| 统一 image 调用 | 消除此前 image/name 参数误用；Python 与 CLI 参数方式已区分 |
| build 与显式回叠组合 | 一次程序执行串联保存和视图；不自动标定、不自动判断建筑质量、不自动 finish |
| 精简成功回复 | 折叠重复元数据与正常投影，保留问题、警告、未评范围、原始回执和图像；文本压缩不等于 token 或耗时同比下降 |
| 增量反馈与修复定位 | 减少无法定位的开口问题触发全楼出图，报告具体交点和受影响对象；离线选择差异不冒充实测时间收益 |
| finish_to | 完成真实原生 finish 后发布同字节产物，避免模型自行复制和重造哈希；最新 Windows 权限缺陷已修复 |
| 未知写入与日志恢复 | 保留原异常、候选与回执路径，避免日志失败掩盖构造结果；不盲目重建 |

最近一批集成检查有 84 项定向通过；发布修复另有主库和独立复核各 13 项通过，并完成真实受限环境的零模型构建与发布验证。这些是实现正确性的证据，不是新的模型速度成绩或建筑质量评分。

当前未解决的明确能力缺口包括正常构造路径中的显式坐标/北向证据贯通。新的完全可选领域工具对照、较低能力模型的匹配对照、统一 domain 接入后的自研 runtime 对照均未完成。

## 10 当前问题应怎样拆开

### 10.1 工具可用性与规定路径混在一起

最近实验同时改变了工具、推荐路径、必须完成的原生手续与允许出口。必须区分两个研究问题：规定原生路径是否高效可靠，以及额外提供可选工具是否有净收益。前者的失败不能自动回答后者。

### 10.2 工具会做 不等于模型容易用

模型需要知道哪些能力存在、适合哪种表示、哪些字段必需、哪种拒绝对应哪种修复。已有内核节省了代码，但接口发现、重复声明和修复仍消耗大量模型工作。问题可能是能力不够，也可能是能力已经存在却不可达或不易组合。

这里有一个设计张力：更强约束可以帮助弱模型保持合法输出，却也可能让强模型绕不开某种表示的缺口；更大的自由度允许替代方案，却可能把几何和契约负担重新交给弱模型。需要验证不同模型如何使用同一组能力，不能只凭偏好决定。

### 10.3 几何合法性与建筑可用性存在缺口

已有检查能拦住门不在墙上、重叠、引用错误等真实问题，但合法连接图不保证通道宽度、入口侧和实际交通合理。把全部建筑判断继续写成固定阈值，也可能误伤管井、设备区、开放空间和推断细节。

需要讨论的是：工具如何提供有效的空间证据和构造支持，让模型更容易判断，而不是增加一长串必须消除的提示。底线不能通过压小门、删空间、伪造连接来满足。

### 10.4 首稿后的收益与完成成本没有分清

历史整案在首稿之后花掉约半程。用户认为许多细化不值得；最新局部题甚至保存后完全没有几何修改。但必要审阅、真实缺口补足和发布也属于交付成本，不能全部删掉。

需要区分四类动作：必修的建筑矛盾、已知信息的缺失、可靠交付所需手续，以及可选细化。停止规则应帮助模型在这些类别上决策，而不是把“返工次数少”作为质量标准。简单设置一次或两次修改上限可能控时，却不保证合格。

### 10.5 程序缺陷会吞掉模型与领域能力

发布权限故障是一个明确实例：模型完成构建与原生审阅，却无法公共交付。北向入口缺失则使模型必须研究本不该由它修复的系统表达能力。离线测试通过不能替代实际执行环境下的出口贯通。

需要把“模型没判断出来”“模型选错表示”“工具能力不可达”“工具本身失败”“公共收件器失败”分别记账，才知道下一步应改哪里。

### 10.6 原 runtime 的缓存与上下文仍有独立疑点

早期幸福中心中，自研接入首稿前报告缓存输入约 2%，Codex 对照约 92.8%。后续同订阅文本探针中，HTTP 路径仍未报告缓存命中，而 Codex 同会话续写出现高比例命中。发送体和服务侧条件并不等同，尚不能认定唯一原因或直接折算费用。

历史中尾部状态重排、旧图转文字引用可能破坏部分前缀，但不能解释全部差异。近期 A/B 已共用 Codex runtime，因此不能用旧缓存问题解释这些 B 的全部劣势。自研 runtime 是否值得保留哪些部分，需要另外控制变量。

### 10.7 弱模型收益仍是假说

用户提出的可能性很重要：强模型能临时实现，不代表较弱模型也能。稳定几何、模板复用、宿主与拓扑生成、局部可执行反馈，可能降低任务要求。

但工具通常不能自动补上模型没有识别出来的关键建筑事实；接口学习本身也可能让弱模型更困难。已有单次 6 Sol 利苑失败不能区分这些原因，其他历史读图节点也不能代替同条件的完整对照。

需分别检验：识读是否正确、正确意图能否表达、构造是否可靠、出错能否恢复、是否知道何时完成。若发现模型只适合部分工作，可形成能力适用范围，再考虑分工；不能提前把分工当作未优化工序的补救。

### 10.8 平台价值与模型生成收益需要分别落地

统一接口、可视化、可追溯产物和可替换模型有系统工程价值。但如果要用它们支撑毕设的主要论证，需要展示实际收益，例如降低人工整理和修复量、提高多建筑合并一致性、缩短仿真准备、提高交付成功率。

也不能把平台价值当作放弃用户速度和质量目标的理由。合理的研究结论可能包含不同层次的证据：领域工具降低构造负担，平台降低集成负担，runtime 负责可靠执行；其中哪层没有增益，就明确缩减或复用外部能力，而不必宣称整套系统全部有效或全部无效。

### 10.9 源 BIM 到实际仿真还没有完成本轮验证

历史只读转换探针在 holes、非正交源多边形和 warning 处理等处遇到后端限制，未运行实际仿真。那是旧产物与当时后端的诊断，不是对当前所有能力的完整重测。

不能为了适配后端把正确的建筑改成规则矩形或填掉孔洞。需要明确源空间到仿真区的派生、拆面、坐标北向、语义映射与守恒检查，并单列验证。这也是平台价值可能兑现的重要环节，但不能用尚未完成的仿真能力解释当前额外耗时。

## 11 竞争性解释及缺少的证据

| 解释或假说 | 已有支持 | 还不能确定什么 | 有区分度的验证 |
|---|---|---|---|
| 主要是说明太长 | 有长参考读取和上下文增长 | 缩短输入后总时间是否改善，是否诱发更多追问 | 同能力同出口，仅调整渐进披露，记录完整成本 |
| 原生路径的额外义务吞掉收益 | B 退出路径受限，且必须提供原生绑定 | 完全可选时模型会怎样选择 | 保留相同通用出口的可选工具对照 |
| 领域表达本身不够好 | 长声明、接口误用、已知北向不可达 | 修复后是否足以取得目标收益 | 明确意图到产物的局部构造题与端到端复核 |
| 模型不信任工具 所以重复检查 | 实际出现自写 schema 和几何检查 | 不信任、信息不足或偶然策略哪个主导 | 让工具明确提供已检范围与缺口，观察重复检查是否减少且质量保持 |
| 主要是实现 bug | 发布失败已复现并修复 | 排除 bug 后还剩多少延迟 | 同环境零模型贯通后，冻结版本的新模型测试 |
| 较低能力模型能从工具获益更多 | 确定性编译可省去复杂编程 | 是否被识读或工具选择能力限制 | 同一较低能力模型的通用与可选工具匹配对照 |
| 自研 runtime 接入拖累 | 历史缓存差异和上下文改写 | 服务、计量与输入构造各自贡献 | 同领域能力、同接口下单独换 runtime |
| 主要价值在平台与仿真集成 | 已有统一数据与可视化设施 | 是否真正减少人工与集成工作 | 跨建筑合并、派生与实际仿真的人工量和失败率记录 |

这些解释可以同时成立。目前不宜把任何一项提升为唯一根因，也不应为了证明某一方向而选择性忽略失败样本。

## 12 供讨论的下一轮安排

以下是候选安排，供参与者修改，不是已批准的新实验清单。

### 12.1 先让明确的公共出口问题可测

发布权限已修复，应保持真实执行环境下的贯通验证。北向应从统一声明贯通到参数化、修改、源摘要和审阅绑定；世界北向与局部几何旋转必须分开。不能对所有输入默认填 0°，也不能把局部 frame 的 yaw 当作真北。

对于尚不能表达的字段，应能明确报告能力边界、保留候选并给出合法替代路径。若允许通用补足，必须对最终实际字节重新核验；不能改过源以后沿用不再匹配的原生审阅或哈希。

### 12.2 把三个问题拆开测试

| 条件 | 能回答的问题 | 必须保持的条件 |
|---|---|---|
| 通用工具 | 当前模型独立完成任务的基线 | 原始输入、共同出口、质量底线、预算与计时 |
| 通用工具加完全可选领域能力 | 额外工具与方法的净增量价值 | 通用出口保留，可不用、部分用或混合使用；必要交付义务等价 |
| 规定原生路径 | 原生流程的工程效率、表达完整性和可靠性 | 作为单独机制诊断，不冒充纯工具可用性对照 |

若共同交付需要审阅材料或来源可追溯，通用组也应承担等价义务；若不需要，不能把某组独有的手续混成共同质量要求。原生证据可以是某路线的真实内部产物，不必伪装成所有路线都拥有。

### 12.3 加一个规模受控的较低能力模型筛选

在共同出口和明确缺陷处理好后，可以选一个较低能力或较低成本模型，在两个局部题上各跑一次通用路径和完全可选领域路径，共四次。模型、推理设置、图像输入、环境和预算保持一致，不由强模型暗中补答。

这能筛查“工具是否降低能力门槛”，不能单独证明稳定可靠。若较低能力模型的领域组通过、通用组失败，是值得追查的信号；需要重复和新题确认。若两边都失败，要先定位识读、表达、工具适配或恢复问题，而不是立即换更强模型掩盖原因。

现有强模型结果只能作历史参考。正式声称模型与工具存在不同收益时，应在同版本和同协议下补齐比较，不能把旧强模型原生路径和新弱模型可选路径直接相减。

### 12.4 保持结果和过程两套指标

结果指标至少包括合格交付率、完整交付时间、建筑质量、机器可读信息完整性、整次 token 与实际或可核实估算费用。失败样本保留，统计每次尝试及每次合格交付成本。

过程指标用于归因：首源、首拒绝、文档读取量、工具返回量、回合数、构造和修复、审阅与发布、工具选择和退回通用路径。这些指标不能替代质量，也不能把固定调用顺序当唯一正确策略。

应交错运行并做必要重复，避免只选最快一次。当前两道局部题已经反复用于开发，后续需要保留一题不用于调参的新题，并逐步覆盖纯 mesh 与其他输入组合。局部净收益成立后，再回到幸福中心、利苑完整验收；多 Agent 仍在单 Agent 工序优化之后。

## 13 希望其他模型重点讨论的问题

1. **我们的归因是否仍然有漏洞？** 特别是工具可用性、路径要求、共同出口和原生来源证明是否真正分开了，还有哪些重要混杂因素？
2. **强模型的可选工具应该怎样呈现？** 哪些能力应默认可见，哪些按需展开，如何让模型知道一个工具能省什么、不能表达什么，而不增加一套新的选择仪式？
3. **如何允许通用构造与领域工具混合？** 怎样在不伪造来源、不复用失效审阅的情况下，保留自由出口并统一验证最终产物？
4. **哪些确定性工作最值得工具化？** 优先解决共享拓扑、重复楼层、门宿主、开放围护、局部修改、导出中的哪些，才能减少真实模型工作，而不继续堆工具？
5. **如何帮助较低能力模型？** 工具可能降低的是哪种能力门槛，哪些识读或建筑判断不能由它替代？怎样用最少测试区分能力问题与 harness 问题？
6. **首稿后怎样停止才合理？** 如何区分必须修的问题、缺失已知信息和低收益细化，并在时间预算内完成必要交付？
7. **自研 runtime 保留哪些才有价值？** 如何独立检验接入、上下文、预算和恢复；如果通用 runtime 更好，怎样保留领域积累和产品入口？
8. **平台价值如何实证？** 除单楼生成速度外，哪些人工量、可恢复性、多楼整合或仿真派生指标最能支撑项目价值，同时不回避当前速度目标？
9. **下一轮最小实验应该是什么？** 请给最少的条件、共同合同、测量项和成功失败后的分支，不直接建议再跑大量整楼或多 Agent。
10. **哪些设计应该保留、改造或撤掉？** 请分别指出证据与待测假设，也说明什么结果会使你改变建议。

请直接反驳你不认同的前提，不需要为既有开发辩护，也不要因为强模型能现做就判定领域系统没有价值。建议应说明具体机制、预期可观察变化和失败后的决策，而不只给“简化提示词”“增加缓存”“让模型自主”这样的方向词。

> 请基于这份背景，独立评估 Sim BIM Agent 当前的问题和下一步路线。先指出你认为最关键的三至五个问题，并区分已证事实、合理推测和缺少证据。然后提出最小的架构或接口调整、最有区分度的少量实验，以及什么结果支持保留、修改或放弃相关设计。请重点回答完全可选领域工具对强模型的价值、工具能否降低模型能力门槛，以及如何证明系统性平台与仿真能力的价值。不要默认当前 harness 全部无效，也不要默认已有工具必然有用。不要降低建筑质量底线，不要用更粗结果制造提速，不要把首稿时间当完整交付时间。没有访问原始材料时，请明确哪些判断仅基于本文。
